# 通知窗口协调与排布

## 职责

- `core.rs`：纯请求模型，维护 FIFO、生命周期、revision、展示时长与终态；不读取屏幕或调用窗口 API。
- `notifications.rs`：纯整栈几何计算；输入同一显示环境及实际物理尺寸，输出全部坐标或“放不下”。
- `host/coordinator.rs`：请求状态的唯一写入者，串行处理 IPC、前端就绪、窗口事件和时钟，决定原生操作顺序。
- `host/windows.rs`：原生请求窗口适配层；创建、调整、揭示、确认隐藏、销毁、观察和恢复。
- `runtime.rs`：平台相关的显示环境、DPI、无边框样式和 DWM 操作。
- `host.rs`：应用启动、RPC 路由、前端命令、托盘和历史窗口入口。

Registry 的互斥锁只保护快速读写。原生窗口操作、模板读取及 WebView 控制器回调均不在锁内执行。Tauri 主事件线程只提交请求事件，不能同步等待协调器；否则协调器分发原生操作时会与主线程相互等待。需要返回结果的前端命令使用异步等待。

窗口创建统一在专用工作线程执行，避免 WebView2 同步泵送消息时重入 Wry 的窗口构建上下文。历史窗口继续共享该执行线程，阅读状态与通知排布独立。

## 生命周期

`queued → preparing → ready → shown → confirmed / cancelled / closed / expired / failed`

可更新通知增加非终态 `hidden`：主动关闭或展示超时只收起窗口，保留更新入口。自动超时后普通更新重新入队；主动关闭后只在显式 `reshow: true` 且预算允许时重新入队。复用原窗口，重新准备并确认最新 revision 后展示，实际展示时才消耗再次展示次数。`updatable: false` 关闭更新入口；连续 12 小时无上报进入 `stale` 终态。完整规则见[可更新通知](live-notifications.md)。

1. 接受请求时入队，不提前声明 `shown`；去重只复用同 mode、同 key 的活动请求。
2. dialog 队首在没有活动 dialog 时获得准备资格。
3. notification 队首在没有其他通知正在准备、可见数量少于 3 且完整尺寸能放入时获得准备资格。后续较小通知不绕过队首。
4. 创建窗口后等待内容完成。准备阶段有 15 秒时限，排队不计入此时限。
5. 前端等待当前版本的文字、图片、图表和绘制帧完成，调用 `ui_ready(revision)`。
6. 过期 revision 不揭示窗口；协调器补发最新内容，等待对应版本确认。
7. `ready` 仅表示内容就绪。协调器重新检查实际尺寸、空间和窗口状态，再执行揭示。
8. 原生窗口通过检查后进入 `shown`，才开始展示计时。重复就绪确认与普通内容更新不延长计时；更新显式提供 `duration_ms` 时重新计时。
9. 结束请求时停止计时并移出排布；旧窗口确认隐藏后，立即压紧剩余窗口，再处理下一条准备。
10. 迟到就绪、重复关闭与已结束窗口的销毁事件不能复活请求或重复推进队列。

每个新请求只创建一个以请求 UUID 标识的窗口。工作区变化时隐藏并复用该窗口，不通过同 UUID 重建来恢复，因此旧 HWND 的回调不会被当作另一次创建的就绪确认。

## 几何规则

- 所有通知共享主显示器工作区；通知的 `window.area` 必须为 `work_area`。
- 请求尺寸与边距使用逻辑像素，原生坐标和实测尺寸使用物理像素。
- 每份布局只使用一份工作区和 DPI 快照；边距 16、间距 12，统一按 DPI 缩放。
- 可见通知按提交顺序由下向上排列；不同宽度保持右对齐。
- 第一条贴近工作区右下角，其余条目的底边为前一条顶边减间距。
- 用预计尺寸判断能否开始准备，用原生实际尺寸判断能否揭示和计算重排。
- 单条通知可以占满工作区。多条合计放不下时保持队首等待，内容过长使用内部滚动。
- 正常新增只放置新窗口，保留现有窗口的用户拖动位置。成员退出或显示环境变化时重新压紧整栈。
- 定时健康检查不重设正常窗口的位置。

工作区或 DPI 改变时重新解析尺寸与布局。放不下的上层通知隐藏并以 `ready` 回到等待队首，保留 HWND、内容、首次展示时间和已消耗的展示时长；剩余空间恢复后复用窗口，继续剩余时长。正在准备的较新通知不能越过这些较早通知。

## 原生状态与恢复

`shown` 是已提交的生命周期状态，不等同于每一帧的可见性。每秒检查当前展示窗口：

- HWND 是否仍存在；
- 是否隐藏或最小化；
- DWM cloak 位；
- WebView 控制器是否可见；
- WebView 边界是否与窗口客户区尺寸一致。

应用造成的隐藏、cloak 或 WebView 可见性异常会尝试恢复，连续 3 轮仍不正常才以展示失败结束并补位。异常销毁直接结束请求。系统 cloak 单独处理，普通应用遮挡和失焦不视为失败。通知窗口始终置顶；请求省略 `window.always_on_top` 时默认 `true`，显式设置为 `false` 会被拒绝。

隐藏／销毁失败会保留明确的清理记录并重试；确认隐藏前不让后续窗口覆盖旧窗口。窗口移动的结果通过原生查询确认，失败不会只吞掉错误。

这些检查不能证明 GPU 已绘制每一个像素，也不能把其他应用遮挡误判为隐藏。视觉验收与原生状态诊断仍然互补。

## 历史与诊断

可更新通知保存最新快照及恢复检查点，终态通知归档。主动关闭／撤销只确认当前内容版本，后续内容重新计算未读；旧 revision 的阅读确认不能确认新内容。托盘只依赖已收起或归档且需要阅读的未读记录，排队、准备和展示数量不会直接触发提醒。

`popu host status` 提供：

- `notifications`：活动通知总数；
- `notification_states`：`queued`、`preparing`、`ready`、`shown` 的分别计数；
- `requests`：最多 128 条轻量摘要，超出时 `requests_truncated` 为 true；
- `windows`：本进程请求窗口的实际状态或读取错误；
- `layout_version`：已提交布局版本；
- `closing`：尚在清理的窗口请求 ID。

诊断摘要不携带图表、图片或整份 content，以免大量排队通知让状态查询超过 RPC 帧限制。标准错误记录展示、恢复与失败原因。

## 验证

纯模型测试覆盖严格 FIFO、单个准备窗口、三条展示限制、独立计时、暂停后剩余时长、版本确认、迟到回调与多轮释放。纯几何测试覆盖不同尺寸、负坐标、DPI 间距和工作区容量。

`notification_window` 原生回归使用独立 Named Pipe、生产 RPC 分发、真实协调器和 WebView2，以及内存历史库；覆盖准备超时、旧 revision、严格 FIFO、展示后 HWND 隐藏／DWM cloak／WebView 隐藏恢复、异常销毁、正常超时和八轮真实混合尺寸通知。测试不连接用户的 Host。

```powershell
cargo test --manifest-path src-tauri/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml --test notification_window notification_window_lifecycle -- --ignored --nocapture
```

原生测试需要解锁桌面。已有 Host 占用默认可执行文件时，使用单独的 Cargo `--target-dir`，避免为了编译终止用户的程序。
